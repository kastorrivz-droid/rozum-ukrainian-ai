# 02 — ROZUM_AI_v2 Specification

**Status:** ACCEPTED / WORKING BASELINE  
**Protocol version:** 2.1

## 1. Назначение

ROZUM_AI_v2 задаёт единый JSON-конверт для передачи задач, результатов и контекста между человеком, агентами и внешними ИИ.

## 2. Канонический конверт

```json
{
  "protocol": "ROZUM_AI_v2",
  "protocol_version": "2.1",
  "id": "8f3d9b4a-1122-48a3-b900-7c2a11b06981",
  "timestamp": "2026-08-22T08:50:00Z",
  "sender_id": "agent_gemini_core",
  "key_id": "key-v1",
  "author": {
    "id": "human_vladislav",
    "role": "architect"
  },
  "intent": "inter_ai_task_request",
  "reply_to": null,
  "context": {
    "session_id": "sess_2026_08",
    "state": {"step": 1}
  },
  "data": {
    "task": "crypto_verification",
    "stage": 4
  },
  "question": "Выполнить верификацию RFC 8785 JCS, digests и signature",
  "output_format": "protocol",
  "signature": null
}
```

## 3. Поля

| Поле | Требование | Смысл |
|---|---|---|
| `protocol` | обязательно, константа | `ROZUM_AI_v2` |
| `protocol_version` | обязательно | Для этого снимка — `2.1` |
| `id` | обязательно, UUIDv4 | Уникальный идентификатор сообщения и ключ replay-защиты |
| `timestamp` | обязательно | ISO-8601 UTC, окончание `Z` |
| `sender_id` | обязательно | Техническая идентичность отправителя |
| `key_id` | обязательно для криптопрофиля | Идентификатор ключа; материал ключа в конверт не помещается |
| `author.id` | обязательно | Автор намерения или исходной задачи |
| `author.role` | обязательно | Семантическая роль автора |
| `intent` | обязательно | Машиночитаемая цель сообщения |
| `reply_to` | обязательно, UUID/null | Ссылка на исходный `id` для ответа |
| `context.session_id` | обязательно | Идентичность логической сессии |
| `context.state` | объект | Явное состояние процесса |
| `data` | объект | Полезная структурированная нагрузка |
| `question` | строка | Человеко-читаемая задача или вопрос |
| `output_format` | строка | Ожидаемый вид результата |
| `signature` | Base64/null | Реальная подпись или `null`; псевдоподпись запрещена |

Дополнительное поле `message_type` допускается как совместимое расширение, но `intent` остаётся обязательным.

## 4. Инварианты запроса и ответа

1. Новый запрос получает новый UUIDv4 в `id`.
2. Ответ получает собственный новый UUIDv4.
3. Ответ устанавливает `reply_to` равным `id` входного сообщения.
4. Ответ сохраняет `context.session_id` исходной сессии.
5. Изменение состояния отражается в `context.state`, а не скрывается только в тексте.
6. Если участник не может создать настоящую криптографическую подпись, он передаёт `signature: null`.
7. Неподписанный пакет может использоваться в ручном доверенном мосте, но не считается прошедшим Stage 4.

## 5. Каноническая строка подписи

Профиль, проверенный `CVT-001`, использует UTF-8 строку:

```text
ROZUM_v2_SIG:<protocol_version>:<id>:<timestamp>:<sender_id>:<key_id>:<author.id>:<author.role>:<intent>:<sha256(JCS(context))>:<sha256(JCS(data))>:<sha256(UTF8(question))>:<output_format>
```

Хэши записываются строчными шестнадцатеричными символами. Поле `signature` не входит в подписываемый материал. Точный порядок и кодирование определены в `08_SECURITY_DESIGN_DOCUMENT.md`.

## 6. Обработка

Получатель применяет пять стадий:

1. Schema Validation.
2. Semantic Check.
3. Fast Replay Pre-Check.
4. Cryptographic Verification.
5. Atomic Replay Store Commit.

Успех предыдущей стадии обязателен для перехода к следующей. Ответ приложения формируется только после допустимого результата пайплайна.

## 7. Совместимость

Версия `2.0` является историческим baseline. Версия `2.1` — текущий рабочий профиль. Участник не должен молча интерпретировать неизвестную версию как `2.1`.
