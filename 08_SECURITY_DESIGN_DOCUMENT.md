# 08 — Security Design Document

**Status:** NORMATIVE / LOCKED  
**Protocol:** ROZUM_AI_v2.1

Этот файл является единым каноническим источником истины по подписи, каноникализации и replay-защите. Историческое имя `08_SECURITY_SIGNATURE.md` поглощено этим документом и не должно существовать как параллельная спецификация.

## 1. Модель угроз

Защита направлена против:

- изменения полей сообщения после подписания;
- выдачи одного отправителя за другого;
- повторной доставки ранее принятого `id`;
- расхождения байтов подписи между реализациями;
- подмены реальной подписи правдоподобной строкой;
- гонки между параллельными получателями при фиксации replay-состояния.

Криптография не доказывает истинность содержимого и не заменяет авторизацию действия.

## 2. Пятистадийный пайплайн

### Stage 1 — Schema Validation

Проверяются обязательные поля, типы, `protocol`, версия, UUIDv4 и базовые форматы. Ошибка завершает обработку.

### Stage 2 — Semantic Check

Проверяются временное окно, допустимость `intent`, соответствие `sender_id`/`key_id`, наличие сессии, правила `reply_to` и контекстные ограничения.

### Stage 3 — Fast Replay Pre-Check

Быстрый кэш или Bloom-фильтр может обнаружить вероятный повтор до дорогой криптографии. Этот слой не авторитетен: ложноположительный результат не должен уничтожать данные и требует проверки постоянного хранилища.

### Stage 4 — Cryptographic Verification

Получатель строит канонические байты независимо, декодирует подпись, проверяет формат профиля и выполняет математическую верификацию. Любое расхождение закрывает обработку.

### Stage 5 — Atomic Replay Store Commit

`id` резервируется атомарно в авторитетном хранилище. Только успешный commit делает сообщение принятым. Конкурентный повтор получает отказ.

## 3. Каноникализация

- `context` и `data` сериализуются строго по RFC 8785 JCS.
- Обычный `json.dumps()` или иной «похожий» сериализатор не является допустимой заменой для произвольного JSON.
- `question` кодируется UTF-8 без нормализации или изменения текста.
- Каждый digest — SHA-256, записанный как 64 строчных hex-символа.
- Поля объединяются ASCII-символом `:` без пробелов и завершающего перевода строки.

Каноническая строка профиля 2.1:

```text
ROZUM_v2_SIG:<protocol_version>:<id>:<timestamp>:<sender_id>:<key_id>:<author.id>:<author.role>:<intent>:<sha256(JCS(context))>:<sha256(JCS(data))>:<sha256(UTF8(question))>:<output_format>
```

## 4. Профиль Ed25519

**Идентификатор:** `ROZUM-SIG-ED25519`

- публичный ключ: RAW 32 bytes;
- подпись: RAW 64 bytes;
- транспортное кодирование: Base64 по RFC 4648 с padding;
- DER-кодированная подпись запрещена;
- ключ выбирается по паре `sender_id` + `key_id`;
- приватный ключ никогда не передаётся в конверте.

`CVT-001` подтверждает детерминированное подписание, приём RAW-64, отказ DER-подписи, обнаружение изменения payload и atomic replay commit.

## 5. Профиль HMAC-SHA256

**Идентификатор:** `ROZUM-SIG-HMAC-SHA256`

- MAC вычисляется по тем же каноническим байтам;
- результат — 32 bytes, транспорт — Base64 RFC 4648;
- сравнение выполняется в постоянном времени;
- один HMAC-ключ не должен использоваться между недоверяющими сторонами;
- ротация выполняется через новый `key_id`.

Включённый `CVT-001` проверяет Ed25519; наличие HMAC-профиля не означает, что для него включён отдельный conformance vector.

## 6. Неподписанный режим

`signature: null` допустим только как явный неподписанный транспортный факт. Получатель обязан либо отклонить такой пакет на Stage 4, либо обработать его в заранее разрешённом ручном доверенном канале с маркировкой `UNSIGNED`. Строка-заглушка запрещена.

## 7. Replay-защита

- ключ уникальности — `id` в пределах поддерживаемой области доверия;
- быстрый pre-check не заменяет атомарное хранилище;
- запись должна иметь срок хранения, достаточный для принятого временного окна и модели угроз;
- повтор после успешного commit получает код `REPLAY_CONFLICT`;
- отказ Crypto не резервирует `id` как успешно принятое сообщение.

## 8. Тестовые ключи

Ключевой материал внутри `tests/interoperability/CVT-001` является **TEST-ONLY / NON-PRODUCTION**. Его повторное использование в реальной системе запрещено.

## 9. Правило изменения LOCKED

Изменение порядка полей, способа каноникализации, кодирования подписи или стадий replay-защиты требует:

1. отдельной записи решения;
2. новой версии профиля;
3. пересчёта всех векторов;
4. независимой проверки;
5. сохранения старых артефактов как исторических, а не их тихой перезаписи.
